# 0011 Default protected-path patterns target structured formats, not lexical keywords

The shipped `defaults/protected-paths.json` protects files by **format and role** rather than by the presence of a keyword in the filename. The previous defaults included three broad lexical patterns — `*secret*`, `*credential*`, and `*token*.json` — that matched the basename of any file whose name contained those substrings. Because `matchGlob` (in `lib/protected-paths.ts`) tests patterns against both the full path and the basename, those patterns blocked legitimate source files such as `credentials.go`, `credential.go`, `secret.go`, `token.go`, `credentials.ts`, and `credentials.test.ts`, as well as configuration files that merely *mention* secrets (`token-handler.json`, `secret-manager.yaml`). The defaults have been replaced by a precise set of patterns anchored on sensitive extensions: `*credentials.{json,yaml,yml,toml}`, `*credential.{json,yaml,yml,toml}`, `*secrets.{json,yaml,yml,toml}`, `*secret.{json,yaml,yml,toml}`, `*token.json`, and `*tokens.json`, alongside the unchanged `.env*`, `*.key`, `*.pem`, `*.p12`, `*.pfx`, and SSH-key patterns.

## Considered options

- **Keep the broad patterns and tell users to exclude via the project layer:** Rejected because the project layer cannot remove baseline patterns (ADR-0009). A `!*secret*` exclusion at the project layer is ignored with a warning, so the false positive is not fixable by the project that suffers from it. The only escape hatch is the machine layer (`~/.pi/agent/security/`), which is per-user and not checked into the repository — meaning every contributor would have to repeat the exclusion locally. Shipping a default that requires every affected user to opt out is the wrong default.

- **Remove `*secret*` / `*credential*` / `*token*.json` and rely solely on the secret scanner:** Rejected because it weakens the guard layer for files that, by convention, carry real secrets (`secrets.json`, `credentials.yaml`, `api-token.json`). The protected-paths guard and the secret scanner are complementary layers (ADR-0002); removing the guard coverage for structured credential files would leave a gap where a file is read and its content reaches the provider before any secret-shape regex fires. Defense in depth is preserved by keeping the guard for *files sensitive by naming convention* and the scanner for *content sensitive by shape*.

- **Replace the broad patterns with a precise set targeting structured credential/secret/token formats (chosen):** The defaults now match files whose **extension** marks them as structured credential/secret/token stores (`.json`, `.yaml`, `.yml`, `.toml`), not files whose basename merely contains a keyword. This keeps `oauth-credentials.json`, `service-credentials.yaml`, `api-token.json`, and `secrets.json` protected while letting `credentials.go`, `secret.go`, and `token.go` be edited. The token patterns are deliberately limited to JSON (matching the previous `*token*.json` scope) so the change does not broaden coverage into YAML/TOML token files that were not covered before.

## Consequences

- Source files named `credentials.go`, `credential.go`, `secret.go`, `token.go`, `credentials.ts`, and `credentials.test.ts` are no longer blocked by the defaults; they can be written and edited without confirmation.
- Structured credential/secret/token files (`.json`/`.yaml`/`.yml`/`.toml`) remain protected: writes are blocked, reads are confirmed (configurable via `readAction`).
- A file like `token-handler.json` or `secret-manager.yaml` — which the previous `*token*.json` / `*secret*` patterns blocked as false positives — is now editable. These filenames describe *roles*, not secrets. Projects that genuinely need to protect such a file can add a specific pattern in `.pi/security/protected-paths.json`.
- The secret scanner (ADR-0002) is unchanged and remains the protection for secret *content* that reaches the provider payload, regardless of the source file's name. A secret embedded in `secret.go` is still redacted before it enters the LLM context.
- The protected baseline (ADR-0009) is unchanged in mechanism: the defaults and machine layers form an immovable baseline; the project layer can only strengthen. The baseline lock now protects a more precise set of patterns.
- Existing users with a machine-layer `protected-paths.json` copied from a prior version of the defaults will retain the broad `*secret*` / `*credential*` / `*token*.json` patterns via the machine layer (the machine config is only copied when absent — `ensureMachineConfigDir` never overwrites). This is accepted: the machine layer is the operator's prerogative, and per constraint #8 the package does not modify user config files. Operators who want the corrected defaults at the machine layer can delete their `~/.pi/agent/security/protected-paths.json` to re-trigger the copy on the next session start, or edit it manually.
- The `matchGlob` function and `evaluateProtectedPaths` in `lib/protected-paths.ts` are unchanged. The fix is a data change in `defaults/protected-paths.json`, not a logic change — there is no hardcoded exception for `credentials.go` or any specific filename.
