# 0010 Audit log writes are not rate-limited

A third rate-limit scope, `audit_writes` (`auditWritesPerSecond`), was implemented in `lib/rate-limiter.ts` (P2-3) and unit-tested, but was never wired into the production `auditLog` path — every entry already reaches the log unconditionally. The field was still present in `defaults/security-policy.json` and the `SecurityLimits` interface, so an operator reading the config could reasonably believe audit flooding was capped when it was not. This ADR records the decision to close that doc/impl gap by removing the scope entirely rather than wiring it.

## Considered options

- **Wire `audit_writes` as a dropping rate limiter (drop writes when over budget):** When the per-second sliding window is exhausted, `auditLog` would return without appending. Rejected: for a tamper-evident forensic log this is a security anti-pattern — an attacker who triggers a flood (e.g. via a tool-call loop, or by causing many Guard confirmations) could push legitimate entries out of the window and suppress the evidence of their real actions. The whole point of the audit log (ADR-0007) is that recorded events cannot be silently lost; a dropping limiter would re-introduce exactly the silent-loss class of failure the chain is meant to make detectable.

- **Coalesce over-budget entries into a summary `audit.flood` record:** Instead of dropping silently, collapse bursts past the budget into a single chained `audit.flood` entry that preserves a count and the time window. Rejected for now: it preserves the chain and surfaces the flood, but adds non-trivial complexity (buffering, periodic flush, ordering invariants) to the critical `auditLog` path whose first guarantee is "never crash the extension". The marginal value is low because rotation already bounds the disk surface (default 10 MB × 3 files ≈ 30 MB cap) and the `tool_calls`-per-turn cap already indirectly bounds the write rate — every audited Guard event originates from a rate-limited tool call. The complexity is not justified given those existing bounds.

- **Remove the `audit_writes` scope entirely; rely on rotation + the `tool_calls` per-turn limit (chosen):** Delete `auditWritesPerSecond` from `SecurityLimits`, `DEFAULT_SECURITY_POLICY`, and `defaults/security-policy.json`; remove the `audit_writes` case from `checkLimit` and the sliding-window state; drop the dedicated tests. Disk fill is bounded by rotation; write rate is bounded indirectly by the `tool_calls` cap; and the doc/impl gap closes — what the operator reads in config is exactly what runs. Future maintainers who want to re-introduce audit write limiting must reconsider the forensic tradeoff documented here before doing so.

## Consequences

- `auditWritesPerSecond` is removed from `SecurityLimits`, `DEFAULT_SECURITY_POLICY`, `defaults/security-policy.json`, and all test fixtures; `RateLimitScope` collapses to `"tool_calls" | "confirmations"`. A leftover fixture field is now a TypeScript excess-property error rather than a silent no-op.
- Audit log writes are never dropped for rate reasons. The "audit must never crash the extension" guarantee and the ADR-0007 tamper-evidence guarantee are both preserved: every recorded event is reachable in the chain, and the only loss vector remains attacker-controlled deletion (which `/security:verify` detects because the attacker cannot re-seal the chain without `audit.key`).
- Disk usage is bounded by rotation (`maxFileSize` × `maxFiles`, default ≈ 30 MB, configurable machine-only via `audit-config.json`).
- Write rate is indirectly bounded by the `tool_calls` per-turn limit: every Guard event originates from a `tool_call`, and a runaway tool-call loop is already blocked by `checkLimit("tool_calls", …)` before it can spawn further audit writes.
- A `lib/audit.ts` rationale comment near `appendChained`/`auditLog` records why audit writes are intentionally unrate-limited and references this ADR, so the next maintainer does not re-add a dropping limiter without reconsidering the forensic tradeoff.
