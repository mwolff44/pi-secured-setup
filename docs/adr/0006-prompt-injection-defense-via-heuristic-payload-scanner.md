# 0006 Prompt-injection defense via heuristic payload scanner

The extension ships zero prompt-injection defense: there are no delimiters between instructions and data, and no detection of injected payloads that arrive via external content (tool results, file contents, bash output). The only available seam for input-side defense is `before_provider_request`, and the extension cannot restructure provider messages (splitting, re-rolling, or inserting structural delimiters between tool-result and instruction messages) without parsing provider-specific message structure, which ADR-0002 forbids. This ADR introduces a heuristic, provider-agnostic payload scanner that detects likely injection payloads, wraps them in content markers, and notifies the user — without blocking.

## Considered options

- **Heuristic regex scanner (string walk) + content marking + notify (no block) (chosen):** A scanner registered on `before_provider_request` recursively walks every string value in the provider payload (the same provider-agnostic walk the secret scanner uses, per ADR-0002), runs a curated set of case-insensitive regex heuristics, and wraps any string that matches in `[UNTRUSTED CONTENT]…[/UNTRUSTED CONTENT]` markers so the model can recognise attacker-controlled segments. An `injection.detected` audit event (warning) is emitted carrying only pattern names and counts — never the verbatim matched text, which would amplify the payload into the tamper-evident log. The user is notified. This is consistent with ADR-0002, adds negligible latency, and introduces no new dependency. It is a Scanner (CONTEXT.md): it detects, marks, and notifies but never prevents the request from proceeding.

- **Separate "guardian" LLM call to classify untrusted content:** Route tool results or the assembled payload through a second, smaller model that classifies content as injected or benign before the main model sees it. Rejected for v1: it adds latency and cost on every turn, introduces a new supply-chain and availability dependency on a second model, and shifts the injection problem to that model (which is itself susceptible). It may be revisited in a future ADR if the heuristic scanner underperforms in practice.

- **Structural delimiter injection between tool-result and instruction messages:** Insert explicit delimiters (or restructure the message array) to separate data from instructions, e.g. wrapping every tool result in fixed boundaries before the next instruction. Rejected because it requires parsing provider message structure — distinguishing tool-result messages from instruction messages — which violates ADR-0002's provider-agnostic string-walk constraint. It would also need per-provider message-shape handling that breaks on every provider API change.

## Consequences

- Detection is provider-agnostic: the scanner walks all string values in the payload exactly like the secret scanner, ignoring differences between Anthropic, OpenAI, Google, and other providers. Switching providers changes nothing.
- Detected segments are wrapped in `[UNTRUSTED CONTENT]\n…\n[/UNTRUSTED CONTENT]` markers in the payload. Each flagged string is wrapped once as a whole (not per line), preserving the surrounding structure.
- An `injection.detected` audit event (severity `warning`) is emitted per turn, carrying the match `count` and a `patterns` map of pattern name → count. The matched text is never logged verbatim, so attacker-controlled content is not amplified into the audit trail.
- The user is notified via `after_provider_response` (mirroring the secret scanner's notify pattern). Notification severity escalates to `error` when the per-turn match count exceeds a configurable threshold, signalling a concerted attempt rather than a stray match.
- The scanner NEVER blocks the provider request — it returns the marked payload, never a block verdict (CONTEXT.md: a Scanner "never prevent[s] a tool from running"). Detection is non-destructive: the request always proceeds, only its text may be annotated.
- Heuristics produce false positives and false negatives by nature. Patterns are anchored (word boundaries, line-start context) to limit false positives on legitimate code, comments, and documentation, and comment lines (`#`, `//`, `/*`, `--`) are skipped for parity with the secret scanner. The threshold and the pattern set are configurable, and the defaults are intentionally permissive.
- Injection rules are loaded machine-only: a project-layer `.pi/security/injection-rules.json` is ignored with a `console.error` warning, so a checked-in file cannot weaken or disable detection. This mirrors the machine-only treatment of `audit-config.json`.
- Patterns are loaded from `injection-rules.json` at runtime rather than hardcoded; invalid regex patterns are skipped during compilation (parity with the bash gate). The machine layer may tune the pattern set and threshold; the defaults layer ships the canonical set.
